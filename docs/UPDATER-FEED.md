# UJANI Public AI updater feed

The desktop updater reads an **unsigned JSON update manifest** from the repository's dedicated `updates` branch. The manifest contains per-platform artifact URLs and Tauri artifact-signature strings; the manifest itself is not signed.

`https://raw.githubusercontent.com/asifshadab33/UJANI-PUBLIC-AI-/updates/latest.json`

This avoids GitHub's `/releases/latest/download` endpoint, which does not select draft or prerelease releases. UJANI currently publishes pre-alpha releases as prereleases, so that endpoint cannot reliably discover them.

Builds that still use the previous endpoint cannot discover feed-enabled releases. Install the first release that uses this feed manually from its approved release page. Later updates are discovered from the `updates` branch.

The release workflow publishes the feed only after the release has passed its signed-artifact verification, evidence capture and production-release approval. It downloads the `latest.json` asset from that approved release, validates the manifest structure, semantic version, and that each artifact URL belongs to the approved repository release. The publisher requires non-empty platform keys and signatures but does not independently verify that each platform key matches the approved release; the release checklist must perform that platform-identity check. It refuses to replace a newer feed with an older or equal version.

The feed contains artifact URLs and per-artifact signature strings. Tauri verifies the downloaded artifact against the public key embedded in the signed production build. The production Tauri configuration sets `requireSignedVersion: true`, so the signed artifact's version binding is enforced. The checked-in public-key value is intentionally empty for development; the signed release workflow injects the public key at build time. Never publish a production installer from a build that lacks that key. That artifact signature does **not** authenticate the manifest's version, platform keys or URLs; the publisher validates those fields against the approved release. The desktop app checks for updates at startup and offers an explicit user-controlled installation; it does not silently replace the running app. The updater displays download progress and applies bounded request timeouts. Tauri verifies the downloaded artifact before installation. On Windows the updater launches its installer and exits the app; on macOS/Linux UJANI relaunches after installation.

If feed publication fails, the already-published release remains available through its release page, but automatic update discovery may remain on the previous version until the workflow is repaired and rerun. The `updates` branch must exist and the release workflow's `GITHUB_TOKEN` must be permitted to push to it; branch rules should restrict ordinary writes and the release job should be the only automated publisher. Verify this permission before the first production release. The initial branch may have no `latest.json`; the first approved release seeds it. The release checklist must verify that the feed's version, every platform key, every artifact URL and every signature string match the approved release. If an already-published manifest contains an incorrect platform URL or signature, stop further publication and verify the approved release asset set. The same-version guard intentionally skips a rerun, so rerunning the publisher alone cannot repair it. Restore the last known-good `latest.json` from its reviewed branch history, or make a reviewed corrective commit on `updates` after revalidating every platform entry against the approved release; record the correction before resuming publication.

Do not publish a manifest from an unapproved draft release, and do not put signing private keys or passwords in this branch. A tested automatic rollback mechanism is not yet established. Before production release, verify database migration compatibility, interrupted installation recovery and a documented manual reinstall/recovery path on each supported desktop OS.
