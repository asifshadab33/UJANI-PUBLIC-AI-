# Personal-to-Enterprise task contract RFC (draft v1)

## Goal and product boundary

Define a narrow, optional bridge from UJANI Public AI to an organisation-controlled UJANI Enterprise service. Public AI remains independently useful on a personal device; Enterprise AI remains independently useful for organisation policy, fleet planning and approved internal workloads. Neither product requires the other to start or operate.

This RFC describes a future protocol boundary. It does not enable transport, remote dispatch, worker execution or data sharing. Remote execution remains disabled until the Enterprise safety gates pass.

## Verified current formats — not wire-compatible

| Concern | Public AI today | Enterprise AI today | Demonstrated gap |
|---|---|---|---|
| Envelope and version | `peer_protocol::TaskEnvelope`, protocol version **2** | `WorkloadManifest` schema version **1**, plus a separate signed admin-approval claim | Different messages, versions and signing domains; neither can be deserialised as the other |
| Task and sender identity | Task ID and recipient device fingerprint; no sender principal, organisation audience or signed key ID in the envelope | Workload ID and target device in approval claims; approver key ID | No common sender, tenant/audience or worker identity envelope |
| Consent | Boolean user-consent claim, signed with the envelope; narrow allow-listed scopes | Signed administrator approval; scheduler policy separately checks device-owner opt-in | No single dual-consent state machine or consent records bound to one shared task digest |
| Capabilities | Peer scopes such as `prompt.read`, `document.read`, `result.write` | Workload class/model and Enterprise capability policy; model inventory has its own capability vocabulary | Access scopes and model/task capabilities are different concepts and must remain separate fields |
| Data and privacy | Peer envelope has no data/privacy classification | Workload manifest has public/internal/confidential/restricted data classification | No shared privacy classification or mapping rule |
| Resources | Peer envelope has no CPU, memory, output or runtime budget | Workload manifest has CPU millis, memory MiB and max runtime | No common bounded resource request; v1 uses MiB (1 MiB = 1,048,576 bytes) for its `memory_mb` fields |
| Expiry and replay | Unix seconds; maximum task lifetime 300 seconds; 16-byte hex nonce; bounded **in-memory** replay guard | Admin approval has its own expiry; device trust and durable ledger have separate replay/sequence primitives | No common nonce/expiry semantics or single transactional replay claim for a delegated task |
| Task state | Public task engine tracks local work; peer envelope has no cross-product status stream | Enterprise ledger tracks reservations/leases; no shared task-status message | No common lifecycle, monotonic status sequence or cancellation acknowledgement |
| Receipt | Public execution receipt v3 is a local hash-chained SQLite metadata record; it is not digitally signed or externally anchored | No interoperable worker execution receipt | No signed worker/organisation-bound receipt or common output-byte verification |

### Important implementation details

- Public peer protocol v2 signs a domain-separated, length-prefixed `serde_json` representation and verifies against a trusted public key supplied out of band. The envelope contains no `key_id` or organisation audience. Its replay guard is in memory; the module comments describe persistence as a future production-adapter responsibility.
- Public receipt v3 records input/output digests, adapter/model provenance, timestamps, network evidence and outcome for supported local operations. It is not the signed receipt required for a remote task.
- Enterprise's workload manifest is a bounded scheduler input, not an authorisation grant. Its signed administrator approval binds the workload/device/class/resource limits, approver key ID, manifest digest and expiry. The durable device-trust registry is a persistence primitive that accepts externally supplied integrity material and can use an external monotonic anchor; this is not a deployed authenticated ingestion service or proof of production KMS custody.
- The shared `model-runtime-inventory-v1` schema is already byte-for-byte identical in both repositories. It is a separate, privacy-minimised capability/resource report; it must never carry prompts, files, credentials or conversation history and it does not authorise a task.
- Current v1 limitation: the descriptor reports host platform/architecture and accelerator observations, but does not declare per-model OS/accelerator compatibility or per-capability provenance. Consumers must preserve **Unknown** unless verified runtime metadata or a signed catalogue establishes compatibility; never infer it from hardware presence or a model name. Device trust, user consent, worker-owner opt-in and organisation-admin approval are enforced by authenticated enrollment/transport/task policy, not implied by an inventory payload. Enterprise's typed matcher is side-effect-free, not a live ingestion service or operator-console model inventory view; Public's live discovery currently targets Ollama. A future v2 may add per-model compatibility and finer-grained evidence; keep strict v1 unchanged.

## Proposed language-neutral v1 message set

The shared draft schema is `schemas/personal-enterprise-task-contract-v1.schema.json`. It defines three strict JSON message shapes in one versioned contract:

1. **task_envelope** — task ID and schema version; sender principal/device; organisation/service audience; issue/expiry timestamps; 32-byte random base64url nonce; registered operation and version; exact payload SHA-256, byte length and media type; data and privacy classifications; named access scopes; required model/task capabilities and minimum context; CPU/memory/runtime/output limits; network-access class and explicit bounded destination allowlist; explicit user-consent record; required organisation-admin and worker-owner approvals; target-device constraint and active-enrollment requirement; Ed25519 signature and key ID.
2. **task_status** — task ID, monotonically increasing sequence, lifecycle state, policy version, user/admin/worker-owner consent state (including revocation), bounded reason code and service signature. Receivers reject stale or repeated sequence values.
3. **execution_receipt** — task/input/output digests and `output_byte_length`; organisation and worker device identity; execution location; start/completion times; outcome; optional measured resource usage; references to user, administrator and device-owner consent; policy version; worker-authorised signature. The schema requires a null output digest exactly when `output_byte_length` is zero, and a SHA-256 digest when output bytes exist.

The schema rejects unknown fields and bounds identifiers, all signed integers to the I-JSON safe range (2^53−1), payload size (16 MiB), collection sizes, CPU, memory in MiB, runtime (at most seven days), output size (64 MiB), nonce and signature encodings. The `memory_mb` and `peak_memory_mb` wire names are retained for compatibility within this draft, but their unit is explicitly MiB (1 MiB = 1,048,576 bytes). Runtime policy should normally set a much shorter expiry: **300 seconds from issue to expiry**, matching Public's existing peer-task lifetime. The schema expresses field shape; it cannot prove relative timestamp ordering, cryptographic validity, consent authority, policy approval or resource enforcement.

## Normative security and compatibility rules

- Hash the exact payload bytes before parsing them. Reject a byte-length or SHA-256 mismatch. Never hash a re-serialized payload in place of the received bytes.
- Reject duplicate JSON object keys before semantic parsing. Construct the signature preimage exactly as `UTF8("UJANI-PERSONAL-ENTERPRISE-TASK-V1\0" + message_type + "\0ed25519\0" + key_id + "\0") || JCS(message_without_signature)`, where `message_without_signature` is the complete message object with only its top-level `signature` member removed and JCS is RFC 8785 over UTF-8. The fixed domain prefix binds the message type, schema family and Ed25519 algorithm; the key ID is explicitly included in the prefix, so both `signature.algorithm` and `signature.key_id` remain cryptographically bound even though the signature object is omitted from JCS. Identifiers and message types cannot contain NUL, making the delimiter unambiguous. Verify using the enrolled public key selected by that exact key ID; reject any algorithm other than `ed25519`. Existing Public peer protocol v2 signing bytes are **not** interchangeable with this proposed profile.
- Enrol sender and worker keys out of band. Bind each key to its principal, device, organisation, allowed audience, validity interval and status. Key IDs and self-asserted device IDs are not proof of trust. Rotation and revocation must be checked at acceptance and immediately before execution.
- `network_destinations` contains at most eight lowercase ASCII DNS hostnames using valid labels. IP literals, numeric-only and hexadecimal shorthand address forms (including abbreviated IPv4 forms), ports, URI schemes, uppercase names and trailing dots are not permitted; single-label alphabetic hostnames remain valid. Resolve and enforce the approved hostname at the egress boundary, including DNS-rebinding protection. With `network_access` equal to `none` or `enterprise_internal`, the destination list must be empty; `allowlisted` requires at least one hostname.
- Require TLS with authenticated peers on every hop, or equivalent independently authenticated end-to-end encryption. Signatures and digests provide integrity, not confidentiality.
- Interpret every timestamp as a non-negative UTC Unix-millisecond integer within the I-JSON safe range. Require `expires_at_unix_ms` to be later than `issued_at_unix_ms` and no more than 300,000 ms later; require the user's `granted_at_unix_ms` to be no later than task issue, and `expires_at_unix_ms` to be later than grant time and no earlier than task expiry. Reject expired tasks before admission and again before dispatch. Atomically claim task ID and nonce in durable replay storage before accepting a task. Reject duplicates across concurrent requests, restarts and recovery. `task_status.sequence` and `execution_receipt.sequence` are separate strictly increasing counters scoped to `(task_id, message_type)`; each stream may start at 1, and receivers reject repeated or lower values within that same stream. Receipt completion must not precede start. Reject a task at both admission and immediately before dispatch when `issued_at_unix_ms` is more than 60,000 ms ahead of the receiver's current UTC clock; this is the single maximum clock-skew allowance for v1 and must be applied identically at both checks. The allowance is not added to task expiry or consent validity. A receiver must use a trusted system clock and fail closed when clock quality is unavailable.
- Require the user's explicit grant for the exact task, payload digest, audience, scopes, classifications and resource limits. The `consent.user.binding_sha256` is lowercase-hex SHA-256 of `UTF8("UJANI-CONSENT-BINDING-V1\0") || JCS(B)`, where `B` is a copy of the complete `task_envelope` with only the top-level `signature` member and nested `consent.user.binding_sha256` member removed. This binds task and sender identity, audience, issue/expiry, nonce, operation/version, exact payload digest/length/media type, classifications, scopes, required capabilities/context, resource limits, network policy/destinations, device-trust constraints and the remaining consent record. Do not include the digest in its own preimage. `JCS` means RFC 8785 over UTF-8; arrays retain their transmitted order. The envelope's Ed25519 signature separately authenticates the resulting digest. Enterprise must independently obtain administrator approval and device-owner opt-in. Wire identifiers use the British spelling consistently: `organisation_id`, `organisation_admin` and `organisation_approval_id`. A task cannot become queued, reserved, running or completed until all required authorities approve; the status schema enforces this minimum condition. Terminal `failed`, `cancelled`, `timed_out`, `rejected` and `expired` states require a bounded `reason_code`. Denial, revocation, expiry or unavailable policy evidence fails closed.
- Re-evaluate current policy, device trust, owner opt-in, workload class, capability, quotas, resource headroom, network scope and expiry immediately before dispatch. Enforce CPU, memory, wall-clock, output and isolation limits at the OS boundary. Never execute shell commands or model-generated code.
- Sign receipts with a worker-authorised key. Before consuming output, the client verifies key/organisation/device identity, task ID, input digest, policy/consent references and that the returned byte count equals the signed `output_byte_length`. If the length is zero, require `output_sha256` to be null. If the length is nonzero, require a SHA-256 digest, hash the exact returned bytes and compare the result with the signed digest.
- Keep inventory separate from task content. Enterprise inventory is accepted only from enrolled/authorised devices after required consent; share only pseudonymous model/runtime/resource metadata. Never share prompts or private content as inventory.
- Preserve standalone operation. A Public-only installation never contacts Enterprise. An Enterprise-only installation continues its own policy/fleet functions. A bridge is used only after explicit user action and organisation acceptance; there is no silent cloud fallback or background compute.

## Rollout and current status

The schema is a draft compatibility boundary, not an active protocol. Existing v2 peer envelopes, Enterprise manifests/approvals and Public local receipts must not be relabelled as interoperable v1 messages. A future adapter must explicitly translate a user-approved task into the new envelope and independently verify the Enterprise status/receipt.

Both native Rust v1 decoders reject duplicate top-level keys for `task_envelope`, `task_status` and `execution_receipt`, and each has a nested-object duplicate regression (Public: nested consent state; Enterprise: nested sender identity). Both decoders also reject unknown typed fields and apply the same consent-binding/JCS, Ed25519 domain/key-ID, payload-digest and monotonic-sequence rules. Enterprise's Python validator checks top-level duplicate keys for each message kind; Public PR #239 adds the same per-message coverage while retaining its nested-duplicate and non-standard-JSON-constant checks. Keep these raw-decoder tests in both products; JSON Schema fixtures alone do not satisfy the parser-level gate. The fixed RFC 8785 consent-binding vector is present in both repositories and checked by both validators. Still required before remote worker execution: cross-language Ed25519 signing/verification vectors; Rust/schema parity tests; sender/organisation/worker key enrollment and revocation; durable transactional replay bound to authenticated intake; authenticated transport; atomic consent/policy/lease admission; OS-enforced isolation and egress; signed receipts and exact output verification; crash, timeout, cancellation and rollback recovery. No transport or remote execution is enabled by this RFC.


## Implementation status and ordered compatibility gates (2026-11-12)

- The task-contract v1 schema and model-runtime inventory v1 schema are byte-identical across the two repositories; the model-runtime inventory test vector is also byte-identical. The native Rust v1 verifier implementations are semantically equivalent but remain separately maintained. The Python validators are independent programs rather than byte-identical shared code; their fixtures and assertions are compared through the compatibility checks. This preserves standalone product operation and avoids a third shared runtime dependency.
- Public PR #218 is merged on `main` (native verifier commit `ba377cdebddaf42f56016ee0bc87e9a5e31dd6d5`). The side-effect-free Rust decoder verifies the v1 envelope, status and receipt messages, consent-binding JCS, Ed25519 domain/key-ID, authenticated sender/audience/target context, exact payload bytes, approval state and monotonic sequences. Public main CI and both CodeQL language jobs passed on exact main SHA `fee13745bde927da83616af94e15fb7748d11947`. This verifier does not provide transport, durable replay storage, authenticated enrollment or dispatch.
- Enterprise PR #140 is merged on `main` (native verifier commit `070e479eb7749b90d86b9274528a6275f038f814`). Its side-effect-free Rust decoder implements the same v1 envelope/status/receipt, consent-binding, Ed25519, payload and sequence verification semantics as Public. Enterprise main CI, CodeQL and RustSec passed on exact main SHA `b17648503875b6e3b677dcd335b2783b0aac1bc9`. No authenticated task-ingestion service or adapter yet binds this verifier to durable replay storage.
- There is deliberately no implicit conversion from Public peer protocol v2 or Enterprise WorkloadManifest v1 into the shared contract. The legacy formats lack fields such as a common sender/audience identity, shared privacy classification, consent references and interoperable receipt semantics. Missing trust or consent data must be supplied by authenticated policy context or the request must be rejected; it must never be fabricated.
- **End-to-end interoperability is not complete.** The shared contract is an optional boundary specification and validation foundation only. Remote dispatch and worker execution remain disabled.

Next gates, in order:

1. Bind both native verifiers to authenticated sender/worker enrollment, key rotation/revocation and durable transactional replay; add an authenticated service adapter without introducing runtime coupling.
2. Integrate current user, organisation-admin and worker-owner consent, policy, replay claim and lease reservation into one fail-closed admission boundary; revoke/recheck immediately before any future dispatch.
3. Add cross-language Ed25519 vectors and prove OS-enforced isolation/egress, bounded resources, cancellation/timeout, failure recovery, signed receipts and exact output-byte verification against durable task/lease records. Keep remote dispatch disabled until every gate passes.


### Model inventory v1 limits and future adapter extension

#### Current implementation boundary (2026-11-12)

- **Public AI:** the desktop inventory producer combines OS-reported platform/CPU/RAM/accelerator observations with installed-model metadata from the loopback-only Ollama adapter. Ollama is the only live discovery adapter today; other runtimes are not inferred from process names or catalogue labels. The storage_free_mb field remains unknown. The separate deterministic model_runtime.rs adapter is explicitly a mock, not real inference. Catalogue recommendations do not install or silently select a model; UJANI-managed downloads remain fail-closed until exact artifact provenance and the Ollama daemon's actual model-store path/free space can be verified.
- **Enterprise AI:** the shared schema validator, bounded typed inventory parser and side-effect-free capability/resource matcher are present. Tests cover empty inventories, unsupported runtimes, stale/future evidence, unknown capabilities, insufficient memory and downloadable-only model rejection. There is not yet an authenticated enrolled-device inventory ingestion service or production tenant model-allowlist/distribution service. Operator model views and fleet recommendations are informational; inventory never proves trust, consent or workload authorisation.
- **Consent boundary:** local model choice remains a device-owner decision. Organisation policy may later constrain eligible families/workloads, but cannot silently replace the owner's selected model or expose prompts/files. Device trust, owner opt-in and administrator approval are checked by separate authenticated policy services, not by trusting a self-reported inventory field.

Model/runtime inventory v1 reports host platform and observed hardware/accelerators, runtime identity/version/network scope, model identity/version/size/context, declared task capabilities, bounded memory estimates and model-level evidence source/confidence/freshness. It does not yet express per-capability provenance or model-specific supported-platform/accelerator constraints. Neither product may infer those facts from a provider name, model family or catalogue label. Unknown or unsupported runtime metadata stays unknown. A future inventory schema v2 may add per-capability evidence and explicit model platform/accelerator compatibility constraints; each runtime adapter must populate them only from a documented runtime API, OS observation or appropriately trusted catalogue source. Different runtimes must remain separate least-privilege adapters rather than being treated as behaviourally interchangeable.
